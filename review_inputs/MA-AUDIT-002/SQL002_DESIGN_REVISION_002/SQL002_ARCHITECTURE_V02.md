# SQL-002 architecture v0.2: authority-committed immutable generations

Status: NON_OPERATIVE_DESIGN_PROPOSAL. Frozen subject: `4d654e8ee11c12e8d10ef27b90ea2e84cf43c55e`. No change to F is implied. This architect-authored revision is not an independent review, verified implementation, owner ratification or SQL-002 pass.

## 1. Requirements and deliberate architectural change

Power-loss durable acknowledgement, narrowly delegated trusted automation and exclusion of agents from authorization/publication/administration are confirmed requirements. Coherent-generation consistency A, atomic publication A and delegated cryptographic authentication A remain proposed and unselected. The design below is conditional on those proposed contracts; it does not select them.

The v0.1 local CURRENT rename is no longer authoritative. A separate protected Authority Commit Service (ACS) is the sole logical publication point, monotonic trust anchor, nonce-use ledger, policy/revocation coordinator and durable receipt outbox. CURRENT is only a repairable local cache of a committed ACS tuple. Readers never admit a generation from CURRENT alone. This trades offline availability and a small local-only design for explicit serialization. It is a material proposed architecture change requiring owner review, not a silent claim that separate filesystem writes are atomic.

ACS is a single logical linearizable durable transaction service, isolated from agent and data-host snapshot administration. Its backing implementation must prove atomic transactions and stable acknowledged history; a generic database name, signed checkpoint or local hash chain is insufficient. Concrete provider/deployment is UNSELECTED. No service instance, key or policy is created. Without a qualified ACS, publication/read admission is unavailable, not downgraded to local trust. Split-brain or rollback of ACS violates the proposed supported profile and must be prevented by its independently protected commit index/witness configuration.

## 2. State and invariants

For dataset K=(trust_domain,workspace_id,dataset_id), ACS durably holds current generation digest/sequence, policy epoch/digest, delegated key state, never-reused policy versions, quarantine set, key/delegation quotas, transaction records, consumed authorization IDs, admission job IDs, prepared storage registrations, commit membership, reader pins and receipt events. Root/recovery state is outside data-host snapshots. Transaction identity is `(K, authorization_id)` and immutable request digest; conflicting reuse always rejects. Sequence advances by exactly one; epoch advances monotonically; all are bounded decimal counters with exhaustion fail-closed.

- I1 Single history: one committed successor for a current parent, binding generation digest, sequence, epoch, manifest and authorization digest. Sequence alone never identifies a generation.
- I2 Atomic logical publication: current tuple, membership, consumed authorization/job IDs, quota charge and COMMIT event/outbox obligation change in one ACS durable transaction, or none change.
- I3 Durable content before commit: ACS may commit only a fresh storage-prepared registration for a sealed, completely synced generation whose retention lease cannot expire or be garbage-collected autonomously.
- I4 Revocation ordering: revocation/policy updates, publication and new reader admission serialize in ACS. If revocation precedes commit, the old authorization cannot commit. A signature issued before revocation is not a reservation of authority.
- I5 No ambient authority: producer bytes and metadata cannot authorize a job; only an independently authenticated admitted job under owner-delegated policy can do so.
- I6 No local rollback admission: new readers obtain current committed membership and quarantine decision from ACS; copied CURRENT/registry/receipt cannot substitute. Historical pinned readers are a bounded exception, not a new stale-current admission path.
- I7 Evidence preservation: PREPARED storage evidence exists before commit; COMMIT includes a durable receipt event atomically. Signature/export delivery is a retryable projection, never the truth source for commit.
- I8 Same bytes: consumed bytes are the sealed pinned objects that were verified; manifest includes exact catalog, digest-sidecar and dependent-context roles; authorization binds the manifest, not mutable receipt files.
- I9 No false ACK: ACK requires durable ACS commit, durable local install/cache reconciliation, exact event delivery receipt from the independent audit store and final policy/quarantine check. A lost response changes knowledge, never committed membership.
- I10 Fail closed: missing coordinator, invalid root, unknown state, uncertain sync, expired policy or incompatible profile causes an explicit unavailable/reject outcome, never fallback to unsigned or stale state.

## 3. Trust and authority boundary

Agent/candidate producer can submit untrusted bytes to intake only. It has no signer/publisher/ACS/admin credential, inherited file descriptor, service socket, network token, cloud metadata entitlement or service-manager control. No general-purpose agent tool may execute under a workload identity. Job-runner code/config and callback destinations are not agent writable; subprocess environment and credential forwarding are denied.

A workload authenticator issues short-lived proof bound to principal, job ID, signer audience, operation and request digest through an isolated authenticated channel. A separate admission controller validates an owner-approved job recipe, immutable source/event trigger, allowed transformations, dataset and content policy. Admission is not inferred from agent claims, valid JSON or a valid hash. For example, a constrained ingestion job may accept data from a separately authenticated feed with schema/content checks; an agent-selected replacement lacking that independent trigger rejects. Actual recipes and input trust roots remain owner decisions; until configured, default DENY.

Signer evaluates delegation, admission and exact manifest independently. It retrieves source/job evidence from authenticated services, not candidate-provided URLs or policy. ACS rechecks the delegation/admission chain and quotas at commit; signer ALLOW cannot override ACS. Limits aggregate across keys/workers/retries by delegation/policy bucket in the same ACS transaction. Signer and ACS must use the same normative contract; disagreement rejects.

Storage publisher owns staging/generation files and can register prepared data, request commit and repair cache; it cannot create delegation, change epoch, authorize new job or sign catalog authorization. It may hold only a distinct STORAGE_PREPARED evidence key. Publication receipt signing uses a separate evidence-only ACS exporter key; it cannot authorize datasets or change policy. Independent audit store identity is separate again. Readers are read-only except ACS pin/release requests.

Owner-root administration alone provisions/revokes delegation and recovery/rotation. Root update is a versioned ACS operation signed by existing trusted root and accepted new root, with owner-controlled recovery path for compromise, independently distributed trust update and monotonic checkpoint. If existing root is compromised, ordinary root-signed messages are insufficient: stop affected admissions and require a separately provisioned out-of-band recovery authority. No automatic key regeneration, root trust reset, service fail-open or agent-issued approval. Root recovery details/threshold are unratified; absent provisioning means recovery unavailable.

Trusted configuration, install/backup/restore/GC paths all require dedicated principals and use the same ACS validation. Host root is in the storage TCB, not modeled as defeatable by chmod; compromise triggers quarantine/service withdrawal. ACS administration and audit store must be outside that host's credentials and snapshot failure domain. No legacy file reader may be described as an authenticated v0.2 consumer. Migration would require separate implementation authorization and consumer inventory; F remains unchanged.

## 4. Content graph and immutable storage

See AUTHORIZATION_CONTRACT_V02.json for exact signed types. DAG: payload bytes -> manifest digest = generation_id -> exact-generation authorization -> PREPARED evidence -> ACS COMMIT event -> exported signed receipt -> independent log delivery receipt. CURRENT references committed tuple and event ID. No artifact hashes itself. Manifest inventories exactly three roles, catalog, digest-sidecar, dependent-context; no arbitrary extra payloads. Manifest and authorization are metadata outside their own inventory; prepared intent/outbox/delivery files are protected metadata, not payload inputs. Multiple contexts or other roles require a new versioned schema and review.

Publisher copies producer input into new publisher-owned inodes; never adopt producer hard links, writable FDs or mmaps. Exact paths are fixed ASCII relative names; no symlinks, special files, hard links, mount crossing or case aliases. Exclusive creation, retained trusted root dirfd, ownership/mount checks and no-overwrite generation installation are mandatory. Parent trust validation must include permitted filesystem identity; dirfd alone does not protect writable children. Protected staging permissions prohibit other principals' reads/writes until sealing; publisher itself cannot mutate a registered generation. Only a separate policy-checked GC path may remove it. Read-only permissions do not revoke existing writable descriptors: all publisher writers/mappings must be closed before sealing; verify inode/link metadata and no exposed writable alias. Host-root tampering is outside benign power-loss guarantees and is an integrity incident.

Manifest is JCS encoded. Hash/length validation operates on immutable files; consumers parse the exact verified buffers or retained immutable FDs. No path reopen into unverified bytes. Staging data, manifest, authorization and local PREPARED intent are individually synced, then staging directory; rename staging to the digest-named generation without replacement, sync both changed parent directories and any newly created ancestors. If same generation already exists, verify exact complete metadata and transaction binding; never replace it. Reuse requires explicit matching transaction registration, not filename equality alone.

Prepared registration includes dataset, generation/manifest/authorization digests, parent/sequence, local intent digest, storage identity/profile, fencing token and checked sync outcomes. ACS durably reserves it as PREPARED; storage cannot reclaim it on time expiry alone. Recovery must obtain an ACS ABORTED/GC grant. ACS commit rechecks active prepared registration and storage identity. This assumes honest qualified storage-service assertions; signatures cannot independently prove successful flush.

## 5. Publication and revocation transaction

Detailed T01-T13 transitions are in TRANSACTION_STATE_MACHINE.json. The critical steps are: independently admit job; obtain exact authorization; prepare/seal/sync files and local intent; register PREPARED; call ACS Commit; reconcile local CURRENT and evidence; obtain final ACK receipt.

ACS Commit executes serializably for K and policy/delegation quota state: check authenticated publisher/fencing token, active prepared record, exact request digest, current parent, sequence=current+1, exact authority epoch/policy digest, active signer/delegation, admission validity, expiry/trusted time, resource limits, quarantine and unused authorization/job IDs. In one durable transaction set membership/current, consume IDs, charge quota, mark transaction COMMITTED and append an immutable COMMIT outbox event. Its durable commit is the only publication linearization point. Publication request success is returned only after that commit survives ACS's qualified power-loss model. A local filesystem rename does not linearize publication.

Revocation/policy changes use the same ACS serial order and immediately increment epoch and disable affected grants at that transaction's commit point. Commit ordered after revoke rejects; commit ordered before revoke remains historically committed but may be quarantined. ACS rechecks even if signer or publisher cached policy. Wall-clock expiry is separately enforced by ACS trusted bounded clock, not producer time. Backward/uncertain clock or unavailable authority denies new authorization/commit/admission; restart cannot reset monotonic floors or quota counters. One-use authorization retries return the same transaction result; a new commit needs a new job/authorization and current parent. Rejected requests have durable reasons; uncertain transport is not a rejection.

ACS may be committed even if local CURRENT still points to old data. A new read consults ACS and opens its exact committed generation; stale CURRENT is ignored/repaired, never used as evidence. Data became durable before ACS commit, so this is cache lag rather than partial logical publication. If committed data is unexpectedly unavailable/corrupt, deny reads and ACK, quarantine, retain committed fact, and perform owner-authorized exact-data restore; never substitute old state or mark committed transaction ABORTED.

A service outage can leave a caller without knowledge of the commit outcome. Actual durable membership remains unambiguous: COMMITTED iff ACS contains the atomic commit record. API state OUTCOME_UNAVAILABLE explicitly means the caller cannot determine it; it is not a third kind of commit. Query exact transaction after recovery; never retry with a new ID or infer failure from timeout. No distributed protocol can guarantee knowledge during a partition, so this is a deliberate availability limit, not a claim of impossible synchronous certainty.

## 6. Acknowledgement and receipts

Storage PREPARED evidence is durable before ACS commit. The COMMIT event is durable atomically with commit and contains transaction ID, authorization digest, manifest digest, parent/sequence, policy epoch, prepared evidence digest, authority identity, event index and chain predecessor. Receipt exporter signs exact event bytes with evidence-only key; log accepts idempotently by event ID and payload digest. Conflicting same-ID payload is an incident. Independent log maintains protected append-only sequence/checkpoints, authentic inclusion and consistency evidence and separately controlled witnesses/export; no plain hash chain is accepted as anti-fork proof.

ACK requires: COMMITTED membership; synced, verified local CURRENT cache for that generation (or later committed successor verified by ACS during serialized reconciliation); independent log's authenticated inclusion/delivery receipt for COMMIT event; active eligible generation/non-quarantine decision; ACS atomically records ACK_READY with these references and returns evidence-signed ACK token. ACK is a durable assertion of recoverability of this committed generation under indefinite retention in v0.2, not a promise CURRENT will never advance. Export of ACK_READY itself is retried from durable outbox; it does not recursively require another remote ACK to return the token. Token lost in transit is retrievable; issuer never asserts client actually received it.

If log unavailable after commit, state is COMMITTED_UNACKNOWLEDGED; reads of eligible committed data can succeed, but no durable ACK is returned. If storage sync after cache repair fails, data may still be committed: quarantine local service, withhold ACK and reconcile without republishing. Evidence records syscall observations as service assertions; power-loss proof and BLD-005 linkage remain separate. Recovery events state recovery time and unknown original fields; they do not fabricate original sync/timestamp observations.

## 7. Reader, quarantine and retention semantics

All new reads contact ACS over independently authenticated fresh sessions (challenge-bound responses, trusted service identity, monotonic checkpoint); copied signed responses cannot establish current membership. ACS atomically checks active policy/quarantine, returns current committed tuple and creates a reader pin. Reader opens exactly the digest generation, verifies manifest/authorization/commit membership, reads immutable content and verifies bytes. It may complete on the complete older pinned generation after a newer publication; it cannot pick an arbitrary old generation. Before delivery, ACS validates the pin and current quarantine policy. If quarantine/revocation requiring quarantine serialized before this final check, deny delivery. If final delivery authorization serialized first, bytes may arrive after later revocation; information already authorized cannot be recalled. No claim of instantaneous revocation of in-flight/already-delivered bytes. This bounded delivery race is an explicit proposed contract requiring owner review.

Normal key rotation does not invalidate historical committed membership; authorization expiry prevents new commits, not eligible old reads. Key compromise revocation defaults to quarantine all generations authorized by that key since its activation unless owner-controlled policy supplies a narrower independently evidenced compromise interval. Already committed history is not erased. New read admission and final delivery fail closed for quarantined members. Reattestation creates a new explicitly authorized generation/record under recovery rules, never silently clears history. Temporary signer outage does not authorize offline reads; ACS availability remains required for admission/delivery.

v0.2 performs no GC of committed generations, committed authorizations, membership or required audit evidence. This deliberately avoids inventing an unratified retention horizon and makes every durable ACK's recoverability promise precise. Storage exhaustion denies new preparation/commit rather than deleting promised history. Only never-committed prepared/aborted data can be removed under ACS-issued dataset/digest/fence-specific GC grant after pins/reservations are absent. Every pin/recovery reservation protects required objects. Future committed-data GC needs a new owner-ratified retention contract and design revision.

## 8. Candidate supported profile and failure classes

PROFILE-LINUX-EXT4-LOCAL-PLP-01 is a proposed qualification target, NOT currently supported or verified: Linux 6.6 LTS with exact patch/build/config pinned in qualification receipt; ext4 local filesystem, data=ordered, barriers enabled, no DAX, no network/FUSE/overlay backing, no writable bind aliases; single verified filesystem for generation staging/install/CURRENT; filesystem directory fsync and atomic rename semantics required. Dedicated local NVMe/device/controller must honor flush/FUA and have evidenced power-loss protection; exact model/firmware/controller/cache, mount options and kernel patch must be recorded, not inferred from family name. UPS is not a substitute for flush correctness. No unprotected volatile RAID/controller cache. Profiles with missing identity or undocumented semantics reject.

This profile is not active until independently qualified and separately authorized. ACS and independent audit store require their own equally explicit durable transaction/storage profiles, isolated from data-host snapshot rollback, durable commit indexes and protected root/witness provisioning; no approved provider exists here. Their crashes must preserve acknowledged transactions, quota/epoch/nonce state, event history and root checkpoints. Data-host backups cannot reset them. A whole-ACS restore below a protected checkpoint is a service incident and blocks operation; restoring data requires exact committed membership/digests, never automatic parent rollback.

Process interruption: OS may retain cached writes; recovery queries ACS, validates complete sealed data and resumes idempotent steps. Kernel crash: unsynced state may vanish; only durable sync/ACS boundaries can be assumed. Machine power loss: completed qualified syncs and ACS commits survive under the pinned honest-flush profile; every ACK remains recoverable, subject to explicit no committed-GC rule. Media destruction, firmware lying about flush, privileged host/ACS compromise and correlated loss beyond provisioned durable copies are outside that guarantee; report data loss/integrity incident, stop service, restore exact authenticated bytes if available, never claim success. A stronger media-loss guarantee would require separately specified redundancy and evidence. Pending hardware qualification is a deployment blocker, not a waiver of owner-required power-loss durability.

All write/rename/fsync/open/close errors are checked. Retry interrupted sync only under documented syscall semantics; any ambiguous persistent error marks storage unhealthy, withholds registration/ACK and triggers recovery. EIO, ENOSPC, read-only remount, short writes, delayed writeback errors or failed directory sync cannot be ignored. Readback alone never proves media persistence. Crash matrix enumerates cuts including sync error after visibility.

## 8a. Normative cross-document refinements

These rules govern all transitions and override any shorter descriptions of digest, retry or cleanup elsewhere in this package.

Storage registration includes a fresh never-reused object-incarnation ID bound to transaction ID, generation digest and physical object identity. A GC grant binds that exact aborted transaction, registration, incarnation and fence, not merely a reusable digest path. Storage serializes grant retirement, deletion and reuse. T03/T04 must not reuse a digest path until every previous deletion grant is durably retired; T12 rechecks exact incarnation under the same serialization and can never delete a newer object. A crash resumes only the identical incarnation grant. Committed data remains ineligible for GC.

COMMIT event chains use SHA-256 of JCS unsigned event payloads; previous_event_digest is that payload digest, with all-zero digest only for genesis. commit_event_digest in ACK instead means SHA-256 of the complete canonical signed COMMIT envelope. T07 durably stores exactly one envelope before first export and retries those exact bytes across restart/key rotation; it never re-signs an already stored event under a new key. Independent log identity binds event ID, unsigned payload digest and that fixed envelope digest; ACK references the same envelope and its inclusion receipt. If no envelope was durably stored or exported, signing may be retried; export before durable envelope recording is forbidden. Key rotation preserves verification of previously stored evidence envelopes or quarantines the evidence without fabricating replacement history.

T02 and T05 enforce the normative cross-envelope joins in AUTHORIZATION_CONTRACT_V02.json, not merely independent signature validity. All chain fields are conjunctive constraints; no individually valid foreign admission, workload identity, manifest or delegation can be substituted. Audience means the same configured ACS commit-service identity in delegation, admission and authorization; signer authentication additionally uses a separately configured signer-channel audience outside this signed scope chain.

## 9. Conditional proof, not evidence

Induction on ACS transactions: initial owner-provisioned genesis has explicit dataset/trust-root and committed sequence zero. A PREPARED transaction changes no committed member. A Commit transaction tests current parent/epoch/IDs then changes all I2 fields atomically, preserving unique successor, no reuse and revocation ordering. Any ACS crash preserves either old or new transaction, never a partial update under its qualified contract. Data sync precedes eligible PREPARED and prepared retention forbids deletion, so a committed generation has durable bytes under the honest storage assumption. Local pointer/receipt-export crashes change projections, not membership; recovery derives them from ACS and registered exact digests. New readers consult ACS and pin only eligible committed members, so a local rollback cannot admit old state. Pinned readers consume sealed data and final quarantine validation bounds authority races. ACK_READY requires all durable obligations; lost response is idempotently recoverable.

This is a conditional design argument, not a mechanized proof or an observation of an implemented ACS. Proof depends on linearizable crash-durable ACS, independent monotonic bootstrap, honest qualified storage, enforced principal separation, cryptographic validity, no alias mutation and correct implementation. Violations block operation or invalidate guarantee; the closure matrix lists independent evidence still required. No target/model/fixture tests were executed or authorized.
